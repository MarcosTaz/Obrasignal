# 6. First superiority benchmark must arrive earlier

A major strategic correction is to avoid waiting for the full Contractor Intelligence OS before testing whether the current product is better.

Start a **Decision Superiority Evaluation** using the current canonical/owner-candidate decision stack.

Minimum evaluation unit:

- one contractor profile;
- one fixed market/time snapshot;
- a set of real/synthetic-but-representative opportunities with provenance;
- independent relevance/action labels where available;
- current ObraSignal ranking/decision/reasons;
- simple keyword/CPV baseline;
- manual portal-search baseline where practical.

Metrics should progressively include:

- Precision@5;
- Precision@10;
- false-positive rate;
- missed-relevant opportunities;
- useful opportunities per 10 reviewed;
- time to confident decision;
- reason correctness;
- UNKNOWN/partial-state handling.

No market-accuracy claim from synthetic corpus alone.

### Why this moves up

Without this benchmark, the company can spend months improving scoring sophistication without knowing whether the customer is actually making a better decision.

`DECISION_SUPERIORITY_BENCHMARK = HIGH_LEARNING_VALUE / LOW_ARCHITECTURAL_LOCK_IN`.

# 7. Revenue and moat must share one customer loop

The ideal operating loop is:

`QUALIFIED PROSPECT`
→ `PROFILE`
→ `REAL MARKET SNAPSHOT`
→ `DECISION BRIEF`
→ `CUSTOMER ACTION`
→ `FIRST VALUE`
→ `PAID/TRIAL DECISION`
→ `OUTCOME / FEEDBACK`
→ `MODEL / PRODUCT LEARNING`.

GTM should not validate one product while Engineering builds another.

Every pilot should progressively feed the same questions:

- Were the top opportunities actually useful?
- Was the recommendation understood?
- Did the contractor act?
- What did they ignore and why?
- What information was missing?
- Would earlier knowledge have mattered?
- What blocked pursuit?
- Would they pay to keep this advantage?

This customer loop is the bridge between Spine A and Spine B.
